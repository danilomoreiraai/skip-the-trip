# EasyPanel deployment

The recommended topology uses a native EasyPanel PostgreSQL service and a
Compose service for the migration, API and web application. EasyPanel owns the
public domain and TLS; PostgreSQL remains private.

## 1. Source prerequisite

The current workspace is not a Git repository. Put the project in a Git
repository reachable by the VPS before creating the Compose service. For a
private repository, add the read-only deploy key generated by EasyPanel.

Configure the Compose source with:

- Build path: `/`
- Docker Compose file: `compose.easypanel.yml`

## 2. PostgreSQL

Create a native PostgreSQL service named `postgres`, with database
`skip_the_trip`. Keep it private. Copy its internal connection URL; use that as
`DATABASE_URL` in the Compose environment.

## 3. Application environment

Copy `.env.easypanel.example` into the Compose environment editor and replace
every placeholder. `APP_DOMAIN` is a hostname only, without `https://` or a
trailing slash. Keep the GlitchTip DSNs and database URL in EasyPanel; never
commit the populated values.

The checked-in example currently points to the temporary physical-test center
in Cobh. Restore the official HH5 coordinates after the on-site test; the
application image does not need to change when only these values change.

## 4. Domain and TLS

After the Compose deployment is healthy, add a domain to the Compose service:

- Destination service: `web`
- Container port: `80`
- Internal protocol: `HTTP`
- Public HTTPS: enabled

Create the DNS record pointing the hostname to the VPS before requesting the
certificate. Do not add Compose `ports`; EasyPanel routes the domain directly
to the internal service.

## 5. Verification

Run these checks against the public hostname:

```sh
SMOKE_BASE_URL=https://staging.example.com/api node scripts/smoke-staging.mjs
curl --fail --silent https://staging.example.com/api/health/ready
```

Then create a GlitchTip GET uptime monitor for
`https://staging.example.com/api/health/ready`, expecting HTTP 200.

## 6. Backups and retention

Production completion and restore evidence are tracked in
[#19](https://github.com/danilomoreiraai/skip-the-trip/issues/19). Automated
retention scheduling and monitoring are implemented by the service below.

Follow the [production backup and recovery runbook](backup-recovery.md) to
configure remote encrypted storage, a daily logical backup, failure detection,
and an isolated restore drill. A successful upload is not restore evidence.

The production Compose definition includes a `retention-scheduler` service. It
runs once when the service starts and then every 24 hours by default. Configure
the following values in the EasyPanel Compose environment:

- `REPORT_RETENTION_DAYS`: age threshold for deletion, in days (default `30`).
- `RETENTION_INTERVAL_HOURS`: interval between runs (default `24`).
- `RETENTION_FAILURE_THRESHOLD`: consecutive failures before an alert (default
  `3`).
- `TELEGRAM_BOT_TOKEN` and `TELEGRAM_CHAT_ID`: operational alert destination.

The same Telegram destination is the owned contact point for Prometheus alerts.
The production stack renders Alertmanager configuration from these secrets at
deploy time; generated configuration remains in a private Docker volume and
must never be copied into logs or the repository. Prometheus and Alertmanager
are internal-only services with no public port. The production Prometheus
configuration uses the stable Compose container DNS names registered by
EasyPanel on its external network; the portable staging configuration keeps
using ordinary Compose aliases. If the EasyPanel project or Compose service is
renamed, update `monitoring/prometheus/prometheus.easypanel.yml` and verify both
the scrape target and Alertmanager discovery before considering the deployment
healthy. Follow the
[incident response runbook](incident-response.md) for acknowledgement,
escalation, controlled delivery testing, rollback and recovery verification.

Each run writes one privacy-safe JSON event to the service log. Successful
events contain `deleted_reports`, `deleted_active_votes`,
`deleted_location_authorizations`, `deleted_total`, and `duration_ms`; failed
events contain only duration, failure count, and error class. They never contain
report records, locations, client identifiers, database URLs, or exception
messages.

## 7. Manual execution and recovery

Before a controlled manual production run, confirm that the latest backup is
healthy and record the current retention configuration. In the EasyPanel
terminal for the `retention-scheduler` service, run:

```sh
npm run db:retention:prod
```

The command uses the same `DATABASE_URL` and `REPORT_RETENTION_DAYS` as the
scheduled service and prints `reports.retention.succeeded` with privacy-safe
deleted-row counts by record type and duration. Reports and active votes use the
configured retention cutoff; expired location authorizations are removed on the
next run. Do not override the retention window for an ad-hoc run.

For controlled verification, create test records in an isolated staging
database on both sides of the cutoff, run the command, and verify that only the
older fixture was deleted. In production, verify the log event and confirm that
current reports remain available through the API; do not insert synthetic
production reports.

If an unexpected deletion is suspected, stop `retention-scheduler`, preserve
its logs and configuration, and follow the
[production backup and recovery runbook](backup-recovery.md) to restore into an
isolated database first. Compare the affected time range before deciding
whether to restore production. Restart the scheduler only after the retention
window and recovered data have been validated.
